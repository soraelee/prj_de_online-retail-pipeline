## 1. 구성 목적

이번 프로젝트에서는 Kafka로 수집한 온라인 리테일 이벤트를 Spark Structured Streaming으로 처리한 뒤 PostgreSQL에 적재하고, 이후 Dimension / Mart 테이블을 배치 작업으로 생성한다.

이를 위해 Airflow를 사용하여 다음 작업의 실행 순서를 관리하도록 구성했다.

```
1. Raw 테이블 초기화
2. Spark Streaming 작업 실행
3. Kafka Producer 실행
4. Raw 데이터 적재 확인
5. Dimension / Mart 배치 테이블 생성
```

Airflow는 전체 파이프라인의 실행 순서와 의존성을 관리하는 역할을 담당한다.

---

## 2. Docker 구성 방식

이번 프로젝트에서는 각 서비스의 역할이 다르기 때문에 Dockerfile과 requirements 파일을 분리했다.

```
Dockerfile.spark       → Spark Master / Worker 실행 환경
Dockerfile.collector   → Kafka Producer 실행 환경
Dockerfile.airflow     → Airflow Webserver / Scheduler 실행 환경
```

requirements 파일도 역할별로 분리하여 필요한 라이브러리만 설치하도록 구성했다.

```
requirements.spark.txt     → Spark 실행에 필요한 패키지
requirements.collector.txt → Kafka Producer 실행에 필요한 Python 패키지
requirements.airflow.txt   → Airflow DAG 실행에 필요한 패키지
```

이렇게 분리한 이유는 다음과 같다.

```
1. 서비스별 필요한 라이브러리가 다름
2. Spark, Airflow, Producer의 실행 책임을 분리할 수 있음
3. 특정 서비스 수정 시 다른 컨테이너에 영향을 줄일 수 있음
4. Docker 이미지 빌드와 디버깅이 쉬워짐
```

## 3. docker-compose 서비스 구성

`docker-compose.yml`에서는 다음 서비스를 정의했다.

|서비스|역할|
|---|---|
|zookeeper|Kafka 메타데이터 관리|
|kafka|이벤트 메시지 브로커|
|collector|CSV 데이터를 Kafka topic으로 전송하는 Producer|
|spark-master|Spark Driver / Master 역할|
|spark-worker|Spark 작업 실행 Worker|
|postgres|Raw / Dimension / Mart 테이블 저장소|
|airflow|Airflow Webserver|
|airflow-scheduler|Airflow DAG 스케줄링 및 Task 실행|
|airflow-init|Airflow 메타 DB 초기화|

각 컨테이너는 동일한 Docker network에 연결하여 서비스명으로 통신할 수 있도록 구성했다.

```
collector → kafka:29092
spark     → kafka:29092
spark     → postgres:5432
airflow   → postgres:5432
```

## 5. 실행 자동화 스크립트

전체 컨테이너 실행과 Airflow DAG 트리거를 자동화하기 위해 shell script를 구성했다.

`run_pipeline.sh`는 인프라 컨테이너를 실행하고, Airflow DAG를 unpause한 뒤 실행하는 역할을 담당한다.

> 주의: collector는 Producer 역할이므로 처음부터 실행하지 않고, DAG 내부에서 필요한 시점에 실행한다.

```bash
#!/bin/bash

set-e

echo"1. Start infra containers"
docker compose up-d zookeeper kafka postgres spark-master spark-worker airflow airflow-scheduler

echo"2. Create collector container without starting"
docker compose up--no-start collector

echo"3. Wait for Airflow to load DAGs"
sleep10

echo"4. Show DAG list"
docker compose exec airflow airflow dags list

echo"5. Unpause ingestion DAG"
docker compose exec airflow airflow dags unpause setup_retail_pipeline

echo"6. Trigger ingestion DAG"
docker compose exec airflow airflow dags trigger setup_retail_pipeline

echo"7. Airflow UI: <http://localhost:8081>"
```

실행 방법은 다음과 같다.

```
chmod+x run_pipeline.sh
./run_pipeline.sh
```

## 6. Airflow DAG 구성

현재 Airflow에는 두 개의 DAG를 구성했다.

|dag_id|filepath|역할|
|---|---|---|
|setup_retail_pipeline|setup_retail_pipeline.py|Raw 데이터 수집 및 적재 준비|
|retail_pipeline|retail_pipeline_dag.py|Dimension / Mart 배치 테이블 생성|

DAG를 분리한 이유는 수집 단계와 가공 단계를 구분하기 위해서이다.

```
setup_retail_pipeline
= Kafka Producer와 Spark Streaming을 통해 Raw 데이터를 적재하는 DAG

retail_pipeline
= Raw 데이터를 기반으로 Dimension / Mart 테이블을 생성하는 DAG
```

# 7. setup_retail_pipeline DAG

`setup_retail_pipeline` DAG는 Raw 데이터 적재를 위한 초기 실행 DAG이다.

## 실행 순서

```
reset_tables
   ↓
start_stream_raw_events
   ↓
check_stream_alive
   ↓
run_collector
   ↓
check_raw_count
```

## 각 Task 역할

|Task|역할|
|---|---|
|reset_tables|Raw 테이블 초기화 및 Spark checkpoint 삭제|
|start_stream_raw_events|Spark Structured Streaming 작업 실행|
|check_stream_alive|Spark streaming 프로세스 실행 여부 확인|
|run_collector|Kafka Producer 실행|
|check_raw_count|PostgreSQL Raw 테이블 적재 건수 확인|

---

## 7-1. 테이블 초기화

Raw 데이터는 재실행 시 중복 적재를 방지하기 위해 DAG 시작 시 초기화한다.

```
TRUNCATETABLE raw_retail_events RESTARTIDENTITYCASCADE;
```

또한 Spark Structured Streaming은 checkpoint를 통해 Kafka offset을 기억하기 때문에, 테스트 재실행 시 checkpoint도 함께 삭제한다.

```
docker exec spark-masterrm-rf /tmp/checkpoints/retail_events_raw
```

이를 통해 DAG 재실행 시 Kafka 메시지를 다시 읽을 수 있도록 구성했다.

---

## 7-2. Spark Streaming 실행

Spark Streaming은 Kafka topic인 `retail-events`를 구독하고, 메시지를 읽어 PostgreSQL의 Raw 테이블에 적재한다.

Airflow DAG에서는 Spark Streaming을 백그라운드로 실행한다.

```
docker exec spark-masterbash-lc'
rm -f /tmp/stream_raw_events.log

nohup /opt/bitnami/spark/bin/spark-submit \\
  --master spark://spark-master:7077 \\
  --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.4.1 \\
  --jars /opt/spark-jars/postgresql-42.7.3.jar \\
  /opt/spark-apps/stream_raw_events.py \\
  > /tmp/stream_raw_events.log 2>&1 &
'
```

`nohup`과 백그라운드 실행을 사용한 이유는 Spark Structured Streaming 작업이 일반 배치 작업처럼 바로 종료되는 것이 아니라, 지속적으로 Kafka 메시지를 읽는 작업이기 때문이다.

---

## 7-3. Spark Streaming 실행 확인

Spark Streaming 작업이 실제로 실행되었는지 확인하기 위해 프로세스 확인 Task를 추가했다.

```
docker exec spark-masterps-ef |grep stream_raw_events |grep-vgrep
```

이 Task를 추가한 이유는 Airflow에서 `spark-submit` 명령 자체는 성공하더라도, 실제 Spark Streaming 작업이 내부 오류로 바로 종료될 수 있기 때문이다.

---

## 7-4. Collector 실행

Collector는 Kafka Producer 역할을 한다.

`collector` 컨테이너는 `docker compose up --no-start collector`로 미리 생성만 해두고, DAG 내부에서 필요한 시점에 실행한다.

```
dockerstart-a collector
```

이렇게 구성한 이유는 Producer가 Spark Streaming보다 먼저 실행될 경우, Spark가 아직 Kafka topic을 구독하기 전에 메시지가 발행될 수 있기 때문이다.

따라서 실행 순서를 다음과 같이 보장했다.

```
Spark Streaming 실행
→ Spark Streaming 프로세스 확인
→ Collector Producer 실행
```

---

## 7-5. Raw 적재 확인

Collector 실행 후 PostgreSQL에 데이터가 적재되었는지 확인한다.

```
docker exec postgres psql-U postgres-d retail_pipeline-c"
SELECT COUNT(*) FROM raw_retail_events;
"
```

# 8. retail_pipeline DAG

`retail_pipeline` DAG는 Raw 테이블에 적재된 데이터를 기반으로 Dimension / Mart 테이블을 생성하는 배치 DAG이다.

## 실행 대상

```
dim_customer
dim_product
mart_daily_orders
```

## 역할

```
1. raw_retail_events 테이블을 기준으로 분석용 테이블 생성
2. 고객 / 상품 dimension 테이블 갱신
3. 일자별 주문 mart 테이블 생성
```

이 DAG는 실시간 수집보다는 적재된 Raw 데이터를 기준으로 주기적으로 실행되는 Batch 성격의 작업이다.

---

# 9. 전체 실행 흐름

전체 파이프라인 실행 흐름은 다음과 같다.

```
run_pipeline.sh 실행
   ↓
Docker infra container 실행
   ↓
collector 컨테이너 생성만 수행
   ↓
Airflow DAG 목록 확인
   ↓
setup_retail_pipeline DAG 실행
   ↓
Raw 테이블 초기화
   ↓
Spark Streaming 실행
   ↓
Spark Streaming 실행 확인
   ↓
Collector Producer 실행
   ↓
Kafka topic에 이벤트 전송
   ↓
Spark Streaming이 Kafka 메시지 소비
   ↓
PostgreSQL raw_retail_events 적재
   ↓
retail_pipeline DAG에서 Dimension / Mart 생성
```

# 11. 구현 중 발생한 문제와 해결

## 11-1. Kafka가 Zookeeper 주소를 찾지 못한 문제

### 오류

```
java.net.UnknownHostException: zookeeper
```

### 원인

Kafka 컨테이너가 Zookeeper와 같은 Docker network에 연결되어 있지 않아 `zookeeper:2181` 주소를 해석하지 못했다.

### 해결

Kafka 서비스에도 동일한 network를 추가했다.

```
networks:
  - kafka-network
```

---

## 11-2. Collector 컨테이너가 없던 문제

### 오류

```
No such container: collector
```

### 원인

DAG에서는 `docker start -a collector`를 실행했지만, `collector` 컨테이너가 미리 생성되어 있지 않았다.

### 해결

실행 스크립트에서 collector를 생성만 하고 시작하지 않도록 구성했다.

```
docker compose up--no-start collector
```

---

## 11-3. Spark Streaming이 실행되지 않은 문제

### 오류

```
nohup: failed to run command 'spark-submit': No such file or directory
```

### 원인

Airflow DAG에서 실행되는 shell 환경에서는 `spark-submit` 명령어가 PATH에 잡히지 않았다.

### 해결

`spark-submit`을 절대경로로 실행하도록 수정했다.

```
/opt/bitnami/spark/bin/spark-submit
```

---

## 11-4. Airflow DAG ID 오류

### 오류

```
Dag id retail_pipeline_dag not found
```

### 원인

Airflow CLI에서 DAG를 실행할 때 파일명이 아니라 `dag_id`를 사용해야 하는데, 파일명 기준으로 실행했다.

### 해결

DAG 목록에서 확인한 실제 `dag_id`를 사용했다.

```
docker compose exec airflow airflow dags trigger setup_retail_pipeline
```

또는 build DAG 실행 시:

```
docker compose exec airflow airflow dags trigger retail_pipeline
```

---

# 12. 정리

이번 Airflow 구성에서는 Docker Compose 기반으로 Kafka, Spark, PostgreSQL, Airflow 환경을 구성하고, Airflow DAG를 통해 데이터 파이프라인의 실행 순서를 관리했다.

특히 수집 단계와 가공 단계를 분리하기 위해 DAG를 두 개로 나누었다.

```
setup_retail_pipeline
→ Raw 데이터 수집 및 적재 준비

retail_pipeline
→ Dimension / Mart 테이블 생성
```

이를 통해 단순히 스크립트를 수동 실행하는 방식이 아니라, Airflow를 통해 데이터 파이프라인의 실행 순서, 의존성, 재실행 가능성, 로그 확인 구조를 관리할 수 있도록 구현했다.
